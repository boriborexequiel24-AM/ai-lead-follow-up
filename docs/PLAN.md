# Lead Capture and Follow-Up Agent | Project Plan

## Goal
A working lead follow-up system for a fictional plumbing + HVAC company that a client can try in under a minute. A lead comes in, an AI agent reads it, decides the next step, replies within seconds, and keeps following up until the lead books, says no, or goes quiet. The owner only steps in for prices, emergencies, and anything the agent isn't sure about.

The portfolio already shows lead routing and CRM sync. This project adds:
- An agent that makes decisions, not just a workflow that moves data
- A conversation a visitor can have with the system, live
- A test set that proves the agent picks the right action

The full agent design (menu, guardrails, end states) is in [agent-flow.md](agent-flow.md).

## How it works

```
Website form ─┐
              ├─> n8n: Intake ─> AI: Read lead ─> AI: Pick step ─> Guardrail check ─> Send / Slack / Close
Email (Gmail) ┘        │               │                │                 │                  │
                       └───────────────┴────────────────┴─────────────────┴──────────────────┘
                                         Supabase (leads, messages, decisions)
                                                   │                 │
                                   n8n: Follow-up scheduler   Next.js dashboard (Vercel)
```

1. **Intake.** The form on the demo site and the email workflow both post to one webhook. Duplicates (same email or phone within 30 days) join the existing lead.
2. **Read.** The AI returns fixed fields: real lead or not, trade, job type, urgency, wants price, missing info, one-line summary. The service-area check is a zip list, not AI.
3. **Pick a step.** The AI chooses one action from the menu, with a reason, and writes the message.
4. **Guardrail check.** A Postgres function checks the choice against the rules (no unapproved prices, quiet hours, message limit, unsubscribe). If a check fails, the action becomes `hand_off`.
5. **Act.** Send the reply, post to Slack for approval or an emergency alert, or close the lead.
6. **Replies.** A visitor's reply in the thread (or an email reply) runs the lead back through steps 2 to 5 with the full conversation.
7. **Follow-ups.** A scheduler runs every minute and handles any lead whose next follow-up is due, using the demo clock in demo mode.
8. **Audit trail.** Every decision, its reason, and every message is a row, so each lead has a full timeline.

## Dashboard (what the client sees)
- **Demo company site:** a simple page for the fake company with the quote request form.
- **Conversation thread:** after submitting, the visitor sees the agent's replies and types their own as the customer. Each agent message shows the action it chose and why.
- **Owner view:** leads list with status, the decision timeline per lead, and prices waiting for approval.
- **Metrics:** speed to first reply, % booked, % handed to a person, follow-ups sent.
- **Try a scenario:** buttons that fill the form with a ready-made lead (burst pipe at night, out of area, price shopper, vague message) so anyone can see the edge cases.

## Data model (Supabase, `leads` schema)
Shares the invoice demo's Supabase project. Every table below lives in the `leads` schema, never in `public`.

- `company_profile`: name, service area zips, hours, services, FAQ answers
- `price_items`: job, low price, high price (sample prices)
- `slots`: start time, booked by lead (fake, reset hourly)
- `leads`: contact info, source, AI fields, status, end state, next follow-up time, demo or seeded
- `messages`: lead, direction (in/out), channel, body, sent at
- `decisions`: lead, action, reason, guardrail result, model, timestamp
- `approvals`: lead, drafted price, Slack message ID, approved by, result

## n8n workflows
1. **Intake:** form webhook and Gmail schedule, both into one path
2. **Agent turn:** read, pick, guardrail, act (called by intake, replies and follow-ups)
3. **Approval:** Slack button clicks for prices
4. **Follow-up scheduler:** every minute, due leads only
5. **Cleanup:** hourly, removes visitor leads older than 24 hours and resets slots

## Build phases
1. **Setup.** git init, Supabase project, Slack channel and app, Gmail label, `.env.example`.
2. **Sample data.** Company profile, service area, FAQ, price sheet, slots. About 20 labelled sample leads with the action each should get, plus a few multi-turn conversations. Include tricky ones: gas smell, out of area, vendor pitch, a price hidden in a long message, someone trying to talk the agent into a discount.
3. **Agent brain + eval.** Read and pick-step prompts with structured output. An eval script scores them against the sample leads. Pick the model here (try the cheapest one that scores well).
4. **Guardrails and conversation loop.** The Postgres guardrail function with its own tests, the messages and decisions tables, and reply handling.
5. **Intake.** Form webhook and the Gmail workflow (scheduled search on the label, never Gmail Trigger).
6. **Slack.** Price approval buttons and emergency alerts.
7. **Follow-ups.** Scheduler, demo clock setting, hourly cleanup.
8. **Dashboard.** Demo site with the form, conversation thread, owner view, metrics, scenario buttons. Deploy to Vercel.
9. **Polish.** README with architecture diagram and screenshots, demo video, case study.

## Decisions made
See the Decisions section in [CLAUDE.md](../CLAUDE.md). In short: plumbing + HVAC company, form and email intake, email replies, agent picks from a fixed menu with rule checks, owner approves prices in Slack, conversation thread on the dashboard, fake slots, sample prices, demo clock.

- **Visitor privacy (decided 2026-11-17).** Visitors type names, emails and messages, so nothing they enter is shown publicly:
  - Each visitor sees only their own thread, through a private link with an unguessable ID
  - The public owner view shows seeded sample leads and overall metrics only
  - The form says to use fake details
- **Public demo limits (decided 2026-11-17).** Every visitor message is an AI call, so:
  - 3 leads per visitor per day (rate limit by IP)
  - About 10 visitor messages per thread
  - A daily cap on total AI calls, so the API cost can't run away
  - Visitor leads are deleted after 24 hours by the hourly cleanup

## Open decisions
- **Outbound email service.** Send from Gmail through n8n (free, already connected) or a sending service like Resend (cleaner sender address, better for a client story). Either way, an allow-list means mail can only go to addresses Exequiel controls.
- **Email intake label.** Something no existing filter would ever apply, like `lead-demo`, for the same reason the invoice project uses `invoice-demo`.
- **Project name.** "Lead Capture" is a working name.
